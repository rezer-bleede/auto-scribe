How AI Coding Agents Plan, Use Tools, and Ship Software

Somewhere between autocomplete and a junior engineer lives a new kind of software: the coding agent. Give it a goal — "add rate limiting to this endpoint" — and it reads the codebase, writes the patch, runs the tests, and iterates until things pass. The magic is not one clever model; it is a disciplined loop of planning, tool use, and verification. This article unpacks how that loop works and why it changes what developers spend their days doing.

Beyond Autocomplete

Traditional assistants predict the next tokens in a file. Agents do something fundamentally different: they take an action, observe the result, and decide what to do next. The unit of work shifts from "complete this line" to "accomplish this task." That requires three capabilities stacked on top of the language model — a planner, a set of tools, and a way to check its own work.

The loop itself is simple to describe: gather context, propose a step, execute it, read the outcome, repeat. The interesting engineering is in what each box actually does under the hood.

Planning: Turning Intent into Steps

A raw prompt like "fix the flaky login test" is too vague to execute directly. Agents plan by decomposing the goal into smaller, verifiable units before touching any code. In practice, effective planning looks like:

  • Task decomposition — break the goal into ordered steps: reproduce, diagnose, patch, validate.
  • Explicit task lists — maintain a checklist the model re-reads every turn, so long sessions do not drift from the original goal.
  • Exploration before mutation — run search tools (grep, glob, dependency graphs) to build a mental map of the repo before editing a single file.
  • Replanning on failure — when a test fails or an assumption breaks, the plan is revised rather than the last edit blindly retried.

Good plans are boring and incremental. The agents that fail in demos almost always fail because they tried to do too much in one step, then could not tell which step went wrong.

Tool Use: The Agent's Hands

The model cannot edit files or run commands — it can only request them. Every capability comes from tools exposed through a structured interface, often an MCP server or a built-in tool registry. A typical agent wields:

  • File tools — read, write, edit with exact-match find-and-replace.
  • Shell tools — run builds, tests, linters, and git commands.
  • Search tools — grep the codebase, glob for files, query the web for docs.

A tool call is just structured data. This is roughly what an agent emits to run a test suite, and what it gets back:

{
  "tool": "bash",
  "input": { "command": "pytest tests/test_login.py -x" }
}

{
  "exit_code": 1,
  "stdout": "FAILED test_login.py::test_refresh_token - KeyError: 'exp'"
}

The model reads that failure, forms a hypothesis about the missing claim, opens the relevant file, and proposes a fix. Nothing about this is mystical — it is a very fast developer with perfect recall and no keyboard.

Context Is the Real Bottleneck

An agent's working memory is its context window, and it fills up fast: file dumps, test output, and tool results pile up until the model loses the thread. Serious agent systems spend as much effort on context management as on prompting — truncating large outputs, summarizing completed steps, and aggressively re-injecting the task list. The uncomfortable truth is that agent capability is bounded less by the model's IQ than by how well the harness curates what the model gets to see.

Verification: The Loop That Matters

Unverified generation is just expensive guessing. What separates a usable agent from a toy is that every meaningful change is checked — tests run, linters pass, diffs reviewed. As the saying goes in the eval community:

The model is not the risk. The loop without verification is the risk.

This is also why guardrails exist: permission prompts for destructive commands, sandboxed execution for untrusted input, and human review before anything is pushed. An agent that can verify its own work still cannot be trusted to approve its own pull request.

What Changes for Developers

When implementation gets cheap, judgment becomes the job. In practice that means:

  • Spec-writing replaces code-writing — clear acceptance criteria are the new function signatures.
  • Review becomes the core skill — reading a machine's 300-line diff fast, well, is a superpower.
  • Invest in test suites — agents go exactly as far as your verification lets them.

AI coding agents are not autonomous engineers; they are tireless executors paired with a plan they can barely see past. The teams shipping real value with them treat the agent as the fastest junior on the roster — unlimited energy, zero tenure, and every line of its work held to the same bar as any other contributor's. Build the loop well, and the shipping takes care of itself.
